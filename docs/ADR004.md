## Question

The paper compares several searchers: the Coast Guard's Expanding Square, a greedy searcher,
a random walk, PPO, and a person flying on the site. R5g asks that they share one interface
over the simulator. D023 asks that the reward be computed outside whatever the agent
observes. **What is the one piece of code that flies any of them over a scenario's cloud and
scores the flight, and what exactly does it measure?**

The site already flies searches (`frontend/src/searchRun.js`), but against **one real buoy**:
found or not. That is one coin toss per scenario. ADR003 §5: *"One buoy is an illustration,
not a result."* The episode flies against **the whole Monte Carlo cloud**, where each
particle carries 1/N of the probability, and measures **how much probability the flight
clears**. That number is POS, and it can be averaged and given an interval.

## Evidence

### 1 · Why a replay takes headings, not positions

A recorded ground path already contains the current: the site's keyboard helicopter flies
90 kt over the ground. Replaying those positions in the marker frame would add the current a
second time. In the Gulf Stream the result also exceeds 90 kt relative to the marker, which
the episode refuses. A person's *decisions* were headings, so headings are what is replayed.
The referee then flies them at 90 kt about the marker, exactly as it flies a learned
searcher's headings.

### 2 · The worked example

This is also the test fixture in `tests/search/test_episode.py`.

- **The cloud.** Gaussian, 2 km per axis.
- **One leg.** 2,778 m (one minute at 90 kt) through the centre clears
  [Φ(92.6/2000) − Φ(−92.6/2000)] × [Φ(1389/2000) − Φ(−1389/2000)] = 0.0369 × 0.5126 =
  **1.89 %** of the cloud.
- **A second minute** that clears 1.0 %:
  - POS = **2.9 %**
  - expected time to detection = (60 × 0.019 + 120 × 0.010) / 0.029 = **81 s**
- **The scale.** One window sweeps at most Z = W·V·T ≈ **23.2 km²**, against a median 90 %
  region of 72 km² at 2 h and 108 km² at 3 h (σ = 26.3, array 58847). Every searcher clears a
  fraction of the cloud, and the comparison is about how large that fraction is.

### 3 · Same seed, same cloud

`sar.pipeline.ensemble.run_ensemble` draws its random pushes once per step, whether or not
the step is saved. So a run saving every minute and a run saving every 5 minutes with the
same seed give **bit-identical positions at every fifth minute**. The search window is
therefore *the same cloud* as the scenario run, only seen more often, and a test holds this.

### 4 · First runs on the real ocean, and what they showed (4 Oct)

Setup: four scenarios on a compute node, arrival 2 h after the call, N = 10⁴, σ = 26.3. Each
run is about 2 s including the drift. The scenarios were S02 and S03 (jet), S30 (quiet) and
S35 (quiet).

| Scenario | Expanding Square POS | Sector Search POS | Real buoy |
|---|---|---|---|
| S02 | 0.307 | 0.325 | missed (closest 8.5 km, 7.0 km) |
| S03 | 0.313 | 0.328 | missed (2.9 km, 2.3 km) |
| S30 | 0.308 | 0.331 | missed (4.3 km, 2.7 km) |
| S35 | 0.305 | 0.330 | **found by the Expanding Square at 33 min**; the Sector Search passed 348 m away |

Two things stand out.

1. **POS hardly varies between scenarios.** The marker frame cancels the current's carry, and
   the cloud's spread is set by σ√t, which is the same everywhere. Scenarios differ in where
   the *buoy* is, not in the shape of the cloud.
2. **The Sector Search beats the Expanding Square**, the reverse of what a frozen cloud of the
   same size gives. `scripts/compare_cloud_paths.py` isolates why. The table below holds the
   spread fixed (2.23 km at arrival, 2.62 km at the end) and changes only *how* each particle
   moves through the window (N = 2 × 10⁴, three seeds, seed-to-seed spread ±0.003):

   | Particles move | Expanding Square | Sector Search |
   |---|---|---|
   | not at all | 0.517 | 0.225 |
   | smoothly, each at its own steady velocity | 0.363 | 0.333 |
   | **as a random walk, the engine's model** | **0.310** | **0.331** |

   The engine gives every particle a fresh push of about 204 m a minute, more than twice the
   half-strip. So lanes the Expanding Square has swept fill back in. The Sector Search
   recrosses the datum every few minutes and is barely affected.

   **POS depends on the path model, not only the spread that σ is matched to.** The drifters
   say real departures from the forecast grow as t^1.7–1.9 (vault D028), which is closer to
   the smooth case. This does not change the referee, which is exact for whatever cloud it is
   given. It is a limitation of the drift model's random term as seen by a search (vault
   register L31), and a reason to report the ranking of the patterns with it.

   **Answered the same night (vault D030):** `scripts/fit_random_velocity.py` fits a random
   *velocity* with memory (Taylor 1921) to the drifters' spread at 1–48 h:
   - the fit is within 2 % at every horizon, where one random-walk σ is off by 50 %;
   - it gives σ_u = 0.217 m/s per axis, against HYCOM's measured 0.228, and T_L = 25.7 h.

   Under it, the Expanding Square clears **0.57** at a 2 h arrival, against 0.31 under the
   random walk. The drift half agreed on 6 Oct; the engine change is its own PR.

## The interface

`src/sar/search/episode.py`

| Member | Contract |
|---|---|
| `SearchEpisode(window, marker, speed_ms, sweep_width_m, pod, steps=45, target=None)` | `window` is an `Ensemble` of exactly `steps + 1` frames, 60 s apart, frame 0 at arrival. `marker` and `target` are `MarkerTrack`s in seconds since arrival. Weights are copied and never renormalised. Speed 0 is allowed (the helicopter hovers: the swept capsule becomes a disc) |
| `step(heading_deg)` / `fly(waypoints)` | One step; returns the probability removed. Refuses a path faster than `speed_ms` in the marker frame, and any step after `done` |
| `position`, `offset`, `particles()`, `weight`, `remaining`, `t_s`, `k`, `done` | The state a searcher or an observation builder reads |
| `metrics()` | `pos`, `expected_ttd_s`, `distance_m`, `removed_per_step`, `elapsed_s`, and with a target `found`, `found_s`, `closest_m`, `closest_s` |
| `track()` | Every sub-leg end as `(t_s, lat, lon)`, for drawing and KML |
| `run(policy, episode, decide_every=1)` | Flies to the end and returns `metrics()` |

`src/sar/search/scenario.py`

| Member | Contract |
|---|---|
| `search_window(forcing, start, lat, lon, seed, particles, arrival_s, sigma=CALIBRATED_SIGMA)` | Re-runs the scenario's ensemble at its seed, keeps the 46 frames of the window, and returns them with the marker track from the window's centroid (the common datum, D004) |
| `scenario_search(row, forcing, arrival_s, particles)` | The same from a row of the scenario table, plus the buoy's hourly truth as the target |
| `steady_window(...)`, `steady_marker(...)` | A synthetic cloud carried by a uniform current, and its marker, for tests and the CLI |

The memory cost of the window builder is the full run kept at every step: 39 MB at N = 10⁴,
386 MB at 10⁵ for 4 h. At 10⁶ it needs a keeper that saves the window only; that is not built.

## Verification

- One test per acceptance criterion of #47, plus:
  - closest approach catching a cross-track particle that the start-of-step rule misses;
  - a 4 s pattern leg swept along its waypoints, not the minute's chord;
  - the marker frame carrying a pattern under a uniform current;
  - POS ≤ 1 under repeated passes at POD < 1;
  - a replay reproducing a heading run exactly;
  - the target's contact time matching a hand-computed crossing;
  - the window's every-fifth frame matching a 5-minute run at the same seed;
  - no Gymnasium import anywhere in `sar.search`.
- End to end: the Expanding Square against a fixed heading on a synthetic cloud, and on real
  scenarios on a compute node.

## Consequences

- **#47's body is rewritten** to rows 2, 3 and 7. **#48 becomes `pattern_policy(expanding_square(...))`**
  plus its citations and an end-to-end run.
- **Every scenario carries three things besides the cloud**: the arrival offset, the marker
  track and the buoy's truth.
- **R5b's per-step movement cost is a constant** while speed and window are fixed, so it
  cannot change which searcher wins.
- **Heading searchers turn instantly**, up to 180° between steps, like the patterns (vault
  register L20).

## Not decided here

- **Which arrival offsets** the experiments use. They should be fixed before the first
  baseline run, like D023's Δ.
- **A turn-rate limit** for heading searchers.
- **A window-only keeper** for N = 10⁶.
