# ADR001: Dependency Management Tooling (pip and npm)

> **Amended.** The Python tooling choice below was originally `uv`. That choice is
> withdrawn: the cluster environment does not have `uv` installed, and the account
> cannot install software with elevated privileges. Although `uv` can, in principle, be
> installed to a user-writable location without root access, plain `pip`, which is
> guaranteed to be present in any Python installation, is the more robust choice given
> this constraint, and is adopted here for both the local machine and the cluster
> alike, rather than as a cluster-only exception. The `npm` decision for the frontend is
> unaffected.

## Question

Should a single dependency management tool be adopted for the entire repository, or
should each ecosystem employ its own?

## Decision

**Each ecosystem shall employ its own tool: plain `pip` (with `venv`) for the Python
backend, and `npm` for the JavaScript frontend.** No single tool spans both ecosystems:
neither `pip` nor `npm` manages the other's packages. The question of a single universal
tool therefore does not arise; the substantive choice is which tool to adopt within each
ecosystem, and whether the resulting duplication is justified.

### Python: `pip` and `venv`, with `pyproject.toml` replacing `env/requirements.txt` and
### `env/requirements-lock-win.txt`

The existing two-file arrangement (a direct-dependency `requirements.txt` for
cross-platform resolution, and a Windows-only freeze for exact reproduction) arose
because `pip freeze` does not perform multi-platform resolution: a freeze produced on
Windows will not install on Ubuntu 20.04. This is a genuine constraint, and plain `pip`
does not remove it in the way `uv` would have done. Cross-platform reproducibility is
therefore obtained more modestly here: version ranges are pinned directly within
`pyproject.toml`, rather than resolved into a single lockfile, and both collaborators
install from that one specification rather than from two files that may diverge. This is
a weaker guarantee than a true lockfile would provide, and should be revisited if
dependency drift between machines becomes a practical problem; `pip-tools`
(`pip-compile`), which is itself installable via plain `pip` and requires no elevated
privileges, would be the natural next step at that point.

Adopting `pyproject.toml` also serves a second purpose, independent of the tooling
question: for `src/sar` to be imported from `scripts/`, `tests/` and, in due course, the
frontend's API layer, it must be installed as a package, and `pyproject.toml` is the
appropriate location for that packaging configuration.

In practice: `python -m venv .venv && source .venv/bin/activate && pip install -e
".[dev]"`, on both the local machine and the cluster. Nothing in this sequence requires
software installation beyond what a standard Python distribution already provides.

**A trade-off should be stated explicitly.** This approach supersedes a branch already
prepared by a collaborator, which has been verified against an actual ERA5 retrieval and
926,000 drifter observations. This is not a trivial matter to override unilaterally, and
should be discussed with the collaborator before being merged.

### JavaScript: `npm`

No alternative justifies its cost for a two-person team. Tools such as `pnpm` or `yarn`
offer improvements in speed and workspace management that are not presently required at
this scale. `npm` is bundled with Node.js, requiring no additional installation and no
onboarding overhead. This decision should be revisited should the frontend expand into a
multi-package monorepo.

## Consequences

- No lockfile is produced for the Python backend at present; reproducibility relies on
  pinned version ranges in `pyproject.toml`. This should be revisited (see above) if
  dependency drift is observed in practice.
- `src/sar` becomes installable via `pip install -e .`, which is the mechanism by which
  it is imported from `scripts/` and `tests/` under the revised structure.
- The pinned dependency versions from `env/requirements.txt` must be transferred into
  the `dependencies` field of `pyproject.toml`. This has not been done automatically,
  and the change should not be merged until it is completed and re-verified against the
  same ERA5 and drifter retrieval used to validate the original configuration.
- The continuous integration workflow (`.github/workflows/tests.yml`) installs
  dependencies via `pip` rather than `uv`, consistent with this decision.
